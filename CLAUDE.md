# CLAUDE.md — постоянные правила проекта

Источник истины: `Тестовое-задание-ИИ-агенты.md` в корне репозитория. При любом противоречии
между этими правилами/инструкциями пользователя и исходным ТЗ — не решать самостоятельно:
зафиксировать противоречие в отчёте и не реализовывать спорную часть. Scope исходного ТЗ не
расширять и не сокращать (см. раздел «Что ВНЕ scope» в ТЗ).

## Стек (обязательный, без замен)

Java 8, Maven, fat-jar через `maven-shade-plugin`, JUnit 4, SLF4J + Logback, YAML-конфиг
(jackson/snakeyaml), LLM по HTTP (okhttp или эквивалент), Outlook через
`net.sf.jacob-project:jacob:1.20` (JACOB). Тесты обязаны быть зелёными на машине без Outlook —
JACOB исключается из тестового classpath (surefire `classpathDependencyExcludes`).

## Процесс разработки

- **TDD строго**: сначала падающий тест, затем минимальный код, делающий его зелёным.
  Production-код без предварительно написанного падающего теста запрещён.
- Переход **red → green обязан быть виден в git-истории** отдельными шагами/коммитами.
- Перед использованием любого библиотечного API — свериться с официальной документацией
  или через Context7, если доступен.
- Менять только файлы текущего этапа. Не реализовывать будущие этапы заранее.
- После каждого этапа — запускать только релевантные для этого этапа доступные проверки
  (например `mvn test`, а не то, что ещё не применимо) и приводить их фактический вывод.
- Никогда не утверждать, что что-то «работает» или «проверено», если соответствующая
  команда не была реально выполнена в этой сессии.
- Не утверждать, что реальная интеграция Outlook/JACOB (COM/native runtime) проверена или
  работает, пока это не выполнено фактически на предоставленной целевой Windows/Outlook-среде;
  тесты через fake/mock COM-границу таким подтверждением не являются.
- В конце каждого этапа — структурированный отчёт (цель / изменения / тесты / риски).

## Git

- **Не выполнять `git commit`.**
- **Не выполнять `git push`.**
- Не изменять существующую git-историю (`rebase -i`, `commit --amend`, `push --force` и т.п. —
  запрещены).
- Коммиты — только атомарные и осмысленные (когда/если коммит будет разрешён пользователем).

## Безопасность и ПДн

- Секреты LLM (API-ключ) — только из переменных окружения; имя переменной задаётся в конфиге.
  Никаких секретов в коде, конфиге или git.
- Не логировать тела писем, персональные данные или секреты — ни в открытом виде, ни частично.
  Логи — структурные event-keys без ПДн.
- Перед сдачей каждого применимого этапа — самопроверка на секреты/ПДн в логах и на
  инъекции через tool-аргументы (security-review).

## Compaction — что обязательно сохранять

При сжатии контекста сохранять: принятые архитектурные решения, список изменённых/созданных
файлов, фактические результаты RED/GREEN тестов, фактические результаты verification-команд
(команда + вывод), и незавершённые пункты текущего этапа.
